## Contract

```
producao_registrar(p_chave text, p_itens jsonb, p_consumo jsonb = null, p_notas text = null, p_justificativa text = null) -> jsonb
  p_itens   = [{"produto": uuid, "sabor": uuid|null, "unidades": int 1..1_000_000}]   (≤ 100)
  p_consumo = [{"ingrediente": uuid, "quantidade": number ≥ 0}]  real use, replaces the recipe amount
producao_corrigir(p_registro uuid, p_chave text, p_itens jsonb, p_consumo jsonb = null, p_motivo text)
producao_desfazer(p_registro uuid, p_chave text, p_motivo text)
answer: {registro_id, evento_id, tipo, versao, status, itens, consumo, ajustes, avisos, estoque, repetido}
```
`p_chave`: generated by the phone BEFORE sending (8–100 chars `[A-Za-z0-9:._-]`), reused on every
retry of the same submission. Refusals carry a code in the error HINT for the screen:
`VANT_FALTA_INGREDIENTE`, `VANT_UNIDADES_VENDIDAS`, `VANT_CONSUMO_ABAIXO_DO_MINIMO`,
`VANT_JUSTIFICATIVA_OBRIGATORIA`, `VANT_RECEITA_SEM_RENDIMENTO`, `VANT_CHAVE_CONFLITO`,
`VANT_ITEM_APAGADO`, `VANT_REGISTRO_DESFEITO`, `VANT_SEM_MUDANCA`, `VANT_MOTIVO_OBRIGATORIO`,
`VANT_*_INVALID[OA]S`, `VANT_LOGIN`.

## Typed consumption (`p_consumo`) — review of 22/11

Proven on the first version: with 1 can in stock, 200 brigadeiros with consumption 0 and 50 cakes
from a recipe without a yield were accepted; the milk stayed at 1. Rules now:

| Rule | Why |
|---|---|
| Every recipe ingredient always counts; omitting one = the recipe amount | omission cannot exempt |
| No ingredient below **90 %** of its recipe amount (`producao_reducao_maxima() = 0.10`) | stops "consumption 0" and gradual erosion; the floor is always against the recipe, never against the last correction |
| Any amount different from the recipe, or an ingredient outside it, needs a reason (5–300 letters); in a correction the mandatory reason is that reason | every adjustment is explained |
| Recipe without a yield (`batch_yield ≤ 0`, not `per_unit`) blocks the production | it used to produce with no ingredient; 0 products are in that state today |
| History: recipe and real amount per ingredient, `consumo_ajustado` + `justificativa_consumo` on the event (a CHECK forbids a flag without a reason), the reason is part of the idempotency hash | auditable, cannot be rewritten |

Using MORE than the recipe (loss, burnt batch) is allowed with a reason, limited by the stock.
If 90 % is too strict or too loose for the business, it is one number in one function.

## Account deletion — review of 22/11

`producao_registros.user_id → auth.users ON DELETE CASCADE`, children cascade from it.
Both flows end with `auth.admin.deleteUser`, so both remove the history with the account:

| Flow | What happens to `producao_*` |
|---|---|
| `delete-my-account` | `apagar_dados_do_usuario` already sweeps it (allowed), then `deleteUser` |
| `admin-delete-user` | not in its table list → still there after the list and the profile → removed by the cascade at `deleteUser` |
| service role / owner / postgres deleting rows directly | refused (`VANT_HISTORICO_IMUTAVEL` or no grant) — the earlier service-role exception was removed |

No edge function changed. Tested end to end in case `22_`, including "no history row without an
existing account".

## History integration with the existing screens (strategy only, no screen changed)

Today `production_batches` is written by `produto_produzir`, `produto_produzir_sabores`,
`registrar_producao`, `mercado_concluir` and `ProductActionsModal` (direct insert), is MUTABLE
(`mercado_salvar` re-links rows, `mercado_desfazer` deletes them, owners may delete), and is read
only by the purchase detail (`use-compra-detalhe-query`, rows "Tô no mercado").

**Rule: each production lives in exactly one store.** Old paths keep writing `production_batches`;
the new path writes only `producao_*`. No double write, no backfill.

1. Etapa 3 adds one read-only RPC `producao_historico(desde, ate)` that unions
   `production_batches` (marked `origem = 'antigo'`, no consumption detail, not correctable) and the
   current version of each `producao_registros` (`origem = 'novo'`, with status, version, real
   consumption, adjustments). The two sides are disjoint by construction, so nothing can appear
   twice; a SQL test asserts it.
2. Screens read only that RPC. The "Produzi" button switches to `producao_registrar` per user
   behind a flag read once per submission, so a retry never crosses paths.
3. Etapa 2 (end of the automatic production) moves the purchase detail to the same RPC; until then
   it keeps reading `production_batches` exactly as today.
4. Etapa 5 retires the old writers after the equivalence analysis. Old rows stay as they are,
   readable, forever.

Rejected: writing both stores (a mutable copy that `mercado_desfazer` deletes and owners can edit,
and every reader that sums both counts twice); copying old rows into `producao_*` (their real
consumption is unknown, because the old functions clamped, so it would be invented history).

## Functional equivalence with the old flow

| Behaviour | `produto_produzir` / `_sabores` (today) | `producao_registrar` (new) |
|---|---|---|
| Base recipe | × units / `batch_yield` | same |
| Flavour extras | × flavour units / `batch_yield` | same |
| Product / flavour stock | + units | same |
| `controla_estoque` | set to true | same |
| `per_unit` products | no ingredient at production (sale takes them) | same, plus a warning in `avisos` |
| Missing ingredient | **clamps to 0, production goes through** | **blocks, lists what is missing** |
| Recipe without yield | produces with no ingredient | **blocks** |
| Several products in one go | one call per product | one call, all or nothing |
| Product without recipe that came from a purchase | takes a fraction of the purchase's inputs | **not done** — Etapa 2 decision |
| `production_batches` row | written | **not written** — see integration strategy |
| Duplicate submission | produces twice | returns the first answer |
| Correct / undo | not possible | yes, with reason, from the stored consumption |

## The 4 old failures of `npm run test:sql`

Independent of Etapa 1. Same 4 cases (`01`–`04`), same lines, on a clean checkout of `main`
(`f82ce8a`) with no Etapa 1 file. Cause: `scripts/funcoes-sql.mjs` keys functions by NAME, and
PR #325 defines `banco_reconciliar(uuid, date)` and then `banco_reconciliar(uuid)` in the same file,
so the loader keeps only the second and the cases calling `(uuid, date)` fail. Production is not
affected (both overloads exist there). CI job `sql` is red on `main` since #325. Separate fix.
