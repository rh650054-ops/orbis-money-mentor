## Contract

```
producao_registrar(p_chave text, p_itens jsonb, p_consumo jsonb = null, p_notas text = null) -> jsonb
  p_itens   = [{"produto": uuid, "sabor": uuid|null, "unidades": int 1..1_000_000}]   (≤ 100)
  p_consumo = [{"ingrediente": uuid, "quantidade": number ≥ 0}]  replaces the recipe amount (real use)
producao_corrigir(p_registro uuid, p_chave text, p_itens jsonb, p_consumo jsonb = null, p_motivo text)
producao_desfazer(p_registro uuid, p_chave text, p_motivo text)
answer: {registro_id, evento_id, tipo, versao, status, itens, consumo, avisos, estoque, repetido}
```
`p_chave`: generated by the phone BEFORE sending (8–100 chars `[A-Za-z0-9:._-]`), reused on every
retry of the same submission. Refusals carry a code in the error HINT for the screen:
`VANT_FALTA_INGREDIENTE`, `VANT_UNIDADES_VENDIDAS`, `VANT_CHAVE_CONFLITO`, `VANT_ITEM_APAGADO`,
`VANT_REGISTRO_DESFEITO`, `VANT_SEM_MUDANCA`, `VANT_MOTIVO_OBRIGATORIO`, `VANT_*_INVALID[OA]S`, `VANT_LOGIN`.

## Functional equivalence with the old flow (input for the analysis Rick asked for)

| Behaviour | `produto_produzir` / `_sabores` (today) | `producao_registrar` (new) |
|---|---|---|
| Base recipe | × units / `batch_yield` | same |
| Flavour extras | × flavour units / `batch_yield` | same |
| Product / flavour stock | + units | same |
| `controla_estoque` | set to true | same |
| `per_unit` products | no ingredient at production (sale takes them) | same, plus a warning in `avisos` |
| Missing ingredient | **clamps to 0, production goes through** | **blocks, lists what is missing** |
| Several products in one go | one call per product | one call, all or nothing |
| Product without recipe that came from a purchase | takes a fraction of the purchase's inputs (`mercado_compras`) | **not done** — Etapa 2 decision |
| `production_batches` row | written | **not written** (history lives in `producao_*`) — Etapa 3 decision for the history screen |
| Duplicate submission | produces twice | returns the first answer |
| Correct / undo | not possible | yes, with reason, from the stored consumption |

1. Merge (CI `app`, `sql`, `drift` green). Merging changes nothing in the database.
2. Before, read-only — expected `0, 0, null`:

          (select count(*) from pg_class where relname like 'producao\_%' and relnamespace = 'public'::regnamespace),
          to_regclass('public.producao_eventos');

3. Rick runs the migration file in the SQL Editor (outside minutes :20–:26 and :50–:52, browser
   translation off). It only creates objects; it takes no lock on existing tables except the brief

4. After, read-only — expected `13, 5, 0`:

5. No screen uses it until Etapa 3, so users see no change.

## Rollback

Run `rollback-etapa1.sql`. It refuses if any production was already recorded by the new flow (that
history is data). Tested in case `22_`: drops only `producao_*`, leaves every other table, function,
trigger and row identical, and the migration applies again afterwards.

## What could interrupt the app

- Nothing on deploy: no existing object is altered; no screen calls the new functions.
- Account deletion: the history is immutable, so deletes are allowed only from
  `apagar_dados_do_usuario`, from the service role, and in the FK cascade they start. Tested (case 22).
- `admin-delete-user` deletes from a fixed table list that does not include `producao_*`: those
  rows would stay orphaned, the same as any other table missing from that list today.
